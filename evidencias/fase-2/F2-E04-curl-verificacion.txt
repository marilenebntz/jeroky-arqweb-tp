## Interpretación

- El proxy Nginx responde correctamente por el nombre `jeroky.local`
  (además de por IP), confirmando el punto 5 del Hito 2 (nombre local).
- Códigos de estado observados: 307 (redirect de `/` a `/alumnos`, propio
  del enrutamiento de Next.js App Router en `release/1`, donde Alumnos es
  el único módulo funcional), 200 (módulo Alumnos), 404 (ruta inexistente,
  manejado por Next.js).
- Cabeceras relevantes: `Server: nginx/1.24.0 (Ubuntu)` confirma que el
  proxy inverso está en el camino de la petición; `X-Powered-By: Next.js`
  confirma que la respuesta final proviene del frontend (Nginx hace
  `proxy_pass` directo al puerto 3000, sin modificar el cuerpo);
  `Cache-Control: no-cache, must-revalidate` indica que estas páginas
  dinámicas no son cacheables (dato relevante para el análisis de caché
  del Hito 3).
- El método `OPTIONS` devuelve `400 Bad Request`: Next.js (modo
  desarrollo) no implementa un manejador explícito de `OPTIONS` para
  rutas de página (no es un endpoint de API con CORS configurado). Se
  registra como observación a revisar en Hito 4 si corresponde definir
  manejo de CORS en las rutas de API del backend (puerto 3001).
- El cuerpo de la respuesta 200 incluye, dentro del payload de React
  Server Components, un componente interno "notFound boundary" (parte
  estándar del framework para manejar sub-rutas no encontradas dentro del
  App Router). Esto no indica que la página falle: el código de estado
  HTTP fue 200 y el módulo Alumnos se visualiza correctamente en el
  navegador (ver F2-E01).
